# 5장. 고칠 것은 한 화면에 모아라

## 장면

전조등 전구가 나갔다. 첫 차에서는 전구를 가는 데 5분이면 됐다. 보닛을 열고, 전조등 뒤로 손을 넣어 전구를 돌려 뺐다.

이 차에서는 범퍼 덮개를 풀어야 전조등이 빠지고, 바퀴집 안쪽의 덮개 고정 클립을 빼야 범퍼 덮개가 풀린다. 손을 대야 하는 곳이 세 군데이고, 나는 앞의 것에서 막힐 때마다 다음 것이 있다는 것을 알게 된다.

한 시간 뒤에 새 전구가 켜지고, 풀었던 것도 모두 다시 조였다. 그날 밤, 같은 쪽 안개등이 켜지지 않는다.

범퍼 덮개를 빼느라 안개등 커넥터를 뽑아 두었는데, 전조등 근처에는 그것을 다시 꽂으라고 알려 주는 것이 없었다. 이 차에서 이 작업을 해 본 정비사라면 생각할 것도 없이 꽂았을 것이다.

AI가 내 코드에서 규칙 하나를 바꿀 때, 그 규칙이 몇 군데에 걸쳐 있는지는 무엇이 AI에게 알려 주는가?

## 주장

> AI는 자기가 찾아낸 곳만 고친다. 그래서 한 번의 변경이 건드리는 코드는 한곳에 모아 둔다.

## 왜 그런가: 새 세션은 검색이 찾아 준 파일을 고치는데, 그 파일은 나머지 두 파일을 언급하지 않는다

작은 온라인 쇼핑몰의 주문 서버를 1년 동안 다룬 개발자는 규칙이 어디에 있는지 안다. 손님이 가입할 때 쓰는 이메일 주소에 규칙 하나를 더해 달라고 하면, 그 개발자는 기억만으로 세 군데를 고친다. `settings.py`에 규칙의 값을 넣고, `validation.py`의 표에 손님이 볼 문구를 넣고, `users.py`에 검사를 넣는다.

그 개발자는 입사하고 몇 주 사이에 이 구성을 배웠다. 셋 가운데 하나를 잊는 날에는, 구성을 아는 리뷰어가 그것을 묻는다.

AI는 앞선 세션을 기억하지 못한다. 그래서 새 세션은 파일이 셋이라는 것을 모른다. 세션은 대개 프롬프트에 있는 낱말로 검색하고, 검색에 걸린 파일 가운데 몇 개를 열고, 무언가를 쓸 수 있을 만큼 읽었으면 쓰기 시작한다.

검색이 세션을 `users.py`로 데려갔다고 하자. 거기 있는 클래스에는 검사가 셋 있고, 검사마다 `email_too_long` 같은 오류 코드를 돌려준다. 세션은 네 번째 오류 코드를 돌려주는 네 번째 검사를 더할 수 있고, 그 결과는 다 끝난 변경처럼 보인다. `users.py` 안에는 문구 표를 언급하는 곳이 없다.

그래도 세션이 그 표를 찾을 수는 있다. 그 클래스에는 부모 클래스의 이름이 적혀 있고, 표는 그 부모 클래스 안에 있다.

하지만 부모 클래스의 파일을 여는 것은 읽기를 한 번 더 하는 일이고, 읽을 때마다 컨텍스트 창이 찬다. 세션은 이미 다 된 것처럼 보이는 변경을 손에 쥔 채로 "더 읽자"고 정해야 한다. 어떤 세션은 더 읽어서 표를 찾고, 같은 프롬프트를 받은 다음 세션은 거기서 멈출 수 있다.

이 장에서 "한 화면"은 세션이 파일 하나를 한 번 읽을 때 받아들이는 범위를 뜻한다. 함수 하나, 또는 통째로 읽을 만큼 짧은 파일 하나다. "고칠 것"은 동작 하나를 바꾸려면 손봐야 하는 줄들을 뜻한다. 가입 규칙이라면 검사, 값, 문구가 그것이다.

『클린 코드』도 사람 독자를 두고 비슷한 조언을 한다. 함께 쓰이는 것은 소스 안에서 가까이 두어야 하고, 그럴 만한 이유 없이 여러 파일로 흩어 놓지 말아야 한다. <!-- 원문 대조 -->

파일 셋으로 나눈 구성에는 그럴 만한 이유가 있고, 그 이유는 사람에 관한 것이다. 운영 담당자는 검사를 건드리지 않고 `settings.py`의 값만 바꿀 수 있다. 손님에게 보이는 문구는 표 하나에 모여 있어서 말투가 한결같다. 이제 독자가 AI 세션이고 세션은 그 파일을 하나하나 검색으로 찾아야 하므로, 이 이유들을 다시 따져 볼 때다.

## 코드: 이메일 규칙의 검사와 값과 문구가 파일 셋에서 함수 하나로 옮겨 간다

쇼핑몰의 가입 처리 함수 `register`는 이메일 주소에 규칙 셋을 적용한다. 주소가 비어 있으면 안 되고, 254자를 넘으면 안 되고, 주소의 꼴을 갖춰야 한다. 사람을 위한 버전은 파일 셋이다. 아래에는 두 덩어리로 나눠 실었고, 위에서 아래로 이어 붙이면 파일 하나로 실행된다. 파일 사이의 `import` 줄은 뺐다.

```python
# settings.py: 운영 담당자가 검사를 건드리지 않고 바꿀 수 있는 값
EMAIL_MAX_LENGTH = 254


# validation.py: 쇼핑몰의 모든 처리 함수가 함께 쓴다
import functools


class Validator:
    """모든 검증기의 부모 클래스. 자식 클래스가 broken_rule()을 정의한다."""

    messages = {  # 쇼핑몰이 손님에게 보여 주는 모든 문장
        "email_required": "이메일 주소를 입력해 주세요.",
        "email_too_long": "이메일 주소가 너무 깁니다.",
        "email_invalid": "올바른 이메일 주소를 입력해 주세요.",
    }

    def rejection(self, value):
        """값이 규칙을 어기면 400 응답을, 아니면 None을 돌려준다."""
        code = self.broken_rule(value)
        if code is None:
            return None
        return {"status": 400, "code": code, "message": self.messages[code]}


def validated(validator_class):
    """데코레이터: 검증기가 값을 받아들일 때만 처리 함수를 부른다."""
    def decorate(handler):
        @functools.wraps(handler)
        def wrapper(value):
            return validator_class().rejection(value) or handler(value)
        return wrapper
    return decorate
```

```python
# users.py
import re

EMAIL_SHAPE = re.compile(r"[^@\s]+@[^@\s]+\.[^@\s]+")


class SignupEmail(Validator):
    def broken_rule(self, email):
        """처음 어긴 규칙의 오류 코드를 돌려준다. 없으면 None."""
        if not email:
            return "email_required"
        if len(email) > EMAIL_MAX_LENGTH:
            return "email_too_long"
        if not EMAIL_SHAPE.fullmatch(email):
            return "email_invalid"
        return None


@validated(SignupEmail)
def register(email):
    """가입 요청을 처리한다: 손님 계정을 만든다."""
    return {"status": 201, "email": email}
```

AI를 위한 버전은 규칙 하나를 문장 하나로 쓴다.

```python
# users.py
import re

EMAIL_SHAPE = re.compile(r"[^@\s]+@[^@\s]+\.[^@\s]+")


def rejected(code, message):
    """400 응답: 오류 코드와 손님에게 보여 줄 문구."""
    return {"status": 400, "code": code, "message": message}


def register(email):
    """가입 요청을 처리한다: 손님 계정을 만들거나 이메일을 거절한다."""
    if not email:
        return rejected("email_required", "이메일 주소를 입력해 주세요.")
    if len(email) > 254:
        return rejected("email_too_long", "이메일 주소가 너무 깁니다.")
    if not EMAIL_SHAPE.fullmatch(email):
        return rejected("email_invalid", "올바른 이메일 주소를 입력해 주세요.")
    return {"status": 201, "email": email}
```

두 버전은 모든 주소에 같은 답을 내고, 같은 테스트 넷을 통과한다. 테스트 넷은 멀쩡한 주소, 빈 주소, 255자짜리 주소, `@`이 없는 주소다.

이제 네 번째 규칙을 더한다. 쇼핑몰이 `throwaway.example` 주소를 더는 받지 않기로 했다. 사람을 위한 버전에서는 파일 셋에 수정 셋이 필요하다. `settings.py`에 그 도메인을 넣고, `Validator.messages`에 새 문구를 넣고, `SignupEmail.broken_rule`에 새 검사를 넣는다. 세션이 셋째 수정만 하고, 도메인을 검사 안에 바로 적어 넣었다고 하자.

```python
# users.py, SignupEmail.broken_rule 안, 마지막 return 위
        if email.endswith("@throwaway.example"):
            return "email_blocked"
```

테스트 넷은 여전히 통과한다. 그 도메인으로 가입해 보는 테스트가 없기 때문이다. `SignupEmail().broken_rule("pat@throwaway.example")`을 불러서 `"email_blocked"`를 기대하는 새 테스트도 통과한다. 하지만 손님이 그 주소로 가입하면 `register`는 `KeyError: 'email_blocked'`를 낸다. `Validator.rejection`이 새 오류 코드의 문구를 표에서 찾는데, 표에 그 문구가 없기 때문이다.

새 테스트가 `register`를 불렀다면 그 테스트는 같은 `KeyError`를 내고, 오류를 읽은 세션은 원인을 찾아 나설 수 있다. 그러니 이 오류는 새 테스트가 `register`를 부를 때만 손님보다 먼저 드러난다. `broken_rule`을 직접 부르는 새 테스트는 통과한다.

`register`를 부르는 테스트라도 `settings.py`를 고치지 않은 것까지는 잡지 못한다. 세션이 문구를 더하고 나면 그 테스트는 통과하고, 도메인은 여전히 검사 안에 적혀 있다. 운영 담당자가 막은 도메인을 보려고 `settings.py`를 열어도 이 도메인은 거기에 없다.

AI를 위한 버전에서는 규칙 전체가 두 줄이다.

```python
# users.py, register 안, 마지막 return 위
    if email.endswith("@throwaway.example"):
        return rejected("email_blocked", "다른 이메일 주소를 사용해 주세요.")
```

이 두 줄을 쓰는 쪽에게는, 같은 화면의 바로 위에 예전 규칙 셋이 보인다. 그 하나하나가 그대로 따라 쓰면 되는 완성된 본보기다. 두 줄을 더하면 `register("pat@throwaway.example")`은 오류 코드가 `email_blocked`인 400 응답을 돌려준다.

AI를 위한 버전은 파일 셋이 주던 것을 내준다. 254를 바꾸려면 이제 운영 담당자가 `register`를 고쳐야 한다. 쇼핑몰이 손님에게 보여 주는 문장을 다 읽으려면 이제 코드를 검색해서 찾아야 한다.

이 코드가 보통 어떻게 바뀌는지는 커밋 기록이 보여 준다. `users.py`를 건드린 커밋 대부분이 `settings.py`와 `validation.py`도 함께 건드렸다면, 대부분의 변경에는 파일 셋이 모두 필요했던 것이다. 파일을 나눈 것은 파일 하나만 고치는 변경을 쉽게 하려던 것인데, 그런 변경은 드물었다는 뜻이다.

## 프롬프트: 새 이메일 규칙을 요청하는 한 줄짜리 프롬프트에는 문구도 설정 파일도 나오지 않는다

두 버전에 같은 프롬프트를 준다.

```text
가입 규칙을 하나 더해 줘: throwaway.example 주소는 거절한다.
```

이 프롬프트는 문구에 대해서도, 값을 어디에 두는지에 대해서도 말하지 않는다. 팀 동료에게 하는 요청이었어도 말하지 않았을 것이다.

`가입`으로 검색한 세션은 두 버전 모두에서 `users.py`에 닿는다. 여기 실린 파일들에서 그 낱말은 한 줄, `register`의 설명 문자열에만 나온다.

AI를 위한 버전에서는 그 함수를 읽으면 완성된 규칙 셋이 문구와 함께 보인다. 사람을 위한 버전에서는 그 파일을 읽으면 오류 코드를 돌려주는 검사 셋이 보인다. 변경을 끝내려면 세션은 파일을 둘 더 열어야 하는데, 프롬프트에는 그 파일들이 있다는 실마리가 없었다.

세션이 그 두 파일을 열 수도 있다. 대소문자를 가려 `email`로 검색하면 `validation.py`의 문구 표 세 줄도 함께 나온다. 하지만 세션이 매번 같은 검색을 하지는 않는다. 그래서 어떤 새 세션은 세 군데를 모두 고치고, 다음 새 세션은 한 군데만 고치고 멈출 수 있다.

> **[실행 기록 자리: E4]** 버전마다: 세션이 한 검색, 연 파일, 바꾼 파일, 새 테스트가 부르는 함수. 날짜, 도구, 모델.

프롬프트에 세 군데를 적어 줄 수도 있다. 그 방법은 요청하는 사람이 요청할 때마다 세 군데를 모두 기억하는 동안에만 통한다.

## 근거: 실험 E4는 같은 서버를 파일 1개, 3개, 5개로 구성하고 그 프롬프트를 준다

실험 E4는 주문 서버를 세 가지 구성으로 만든다. 세 구성은 모든 가입 요청에 같은 답을 내고 같은 테스트 넷을 통과한다. 아직 돌리지 않았다. 이메일 규칙은 파일 하나에 있거나(AI를 위한 버전), 셋에 있거나(사람을 위한 버전), 다섯에 있다(사람을 위한 버전에서 문구 표를 `messages.py`로, 데코레이터를 `decorators.py`로 옮긴 것). 구성마다 그 한 줄짜리 프롬프트를 새 세션 10개에 준다.

실행 하나하나는 판정 테스트(AI에게 보여 주지 않고 결과가 맞는지 가리는 테스트)가 판정한다. 판정 테스트는 `throwaway.example` 주소에는 오류 코드와 문구가 든 400 응답을, 다른 도메인과 닮은 도메인 `notthrowaway.example`에는 201을, 기존 테스트 넷에는 예전과 같은 답을 기대한다.

E4는 세션마다 어떤 파일을 열었는지, 그리고 변경이 새 규칙의 어느 부분을 빠뜨렸는지도 기록한다. 값을 `settings.py`에 두는 구성에서 도메인을 검사 안에 적어 넣은 경우는 diff를 보고 센다. 그것은 어떤 테스트로도 보이지 않기 때문이다.

구성마다 10번이면 큰 차이만 눈에 보인다. 세 구성이 비슷하게 통과한다면, 나는 이 장의 주장을 더 큰 저장소로 좁히거나 거둬들여야 한다.

> **[결과 자리: 실험 E4]** 날짜, 도구와 모델. 구성마다: 10번 가운데 판정 테스트를 통과한 실행 수, 실행마다 빠뜨린 부분, 세션마다 연 파일 수와 도구 호출 수.

> **[저자 사례 자리]** 함께 바뀌어야 하는 여러 곳 가운데 AI가 한 곳만 고친 변경: 날짜, 그 여러 곳, AI가 빠뜨린 곳, 그것을 잡아낸 것.

## 사람이 할 일

- [ ] 가장 최근에 AI에게 맡긴 일이 바꾼 코드 파일 하나를 고르고, 그 파일을 건드린 최근 커밋 20개에서 다른 무엇이 함께 바뀌었는지 센다: `git log -20 --name-only --full-diff --format= -- path/to/file.py | sort | uniq -c | sort -rn | head`. 맨 위의 숫자와 비슷한 숫자가 나온 파일은 내 파일과 거의 매번 함께 바뀐 파일이다. `--full-diff`는 빼지 않는다. 이것이 없으면 Git은 내가 지목한 파일만 보여 준다. <!-- 출처: notes/sources.md, git log --full-diff --> 변경 기록 파일과 테스트 파일은 무엇과도 함께 바뀌는 편이므로 건너뛴다. 낮은 숫자도 무시한다. 저장소 전체의 서식을 고친 커밋 하나가 모든 파일에 1을 더하기 때문이다. 이 목록은 변경이 건드렸어야 하는데 건드리지 않은 파일은 보여 주지 못한다.
- [ ] AI가 여러 파일에 흩어진 코드에 규칙을 더했다면 AI가 쓴 새 테스트를 연다. 그 테스트가 AI가 방금 쓴 함수만 부른다면, 처리 함수(여기서는 `register`)를 거치는 테스트를 요청한다.
- [ ] 숫자가 높게 나온 파일 한 쌍을 두고 AI에게 요청한다. 파일 이름은 자기 것으로 바꾼다. "이 규칙에 필요한 것을 settings.py에서 그 규칙을 적용하는 함수 안으로 옮겨 줘. 동작은 바꾸지 마. 옮기기 전과 후에 테스트를 돌리고 두 결과를 다 보여 줘." 자리를 옮길 수 없는 부분이 있으면, 세션이 고치게 될 줄에 주석을 붙여 둔다. 예를 들면 `# 새 규칙에는 Validator.messages(validation.py)의 문구와 settings.py의 값도 필요하다.` 같은 주석이다. 이 주석은 늘 맞게 유지한다. 주석을 읽은 세션은 표가 다른 데로 옮겨 갔다는 것을 알 길이 없기 때문이다.
- [ ] 코드 리뷰 점검표에 질문 하나를 더한다. "이 규칙이 다시 바뀌면, 그 변경은 파일을 몇 개 건드리게 되는가?"

## 이 원칙이 깨지는 곳

어떤 규칙은 모든 처리 함수에서 지켜져야 한다. 누가 로그인했는지, 누가 환불을 해 줄 수 있는지, 세금을 어떻게 붙이는지가 그렇다. 그런 규칙은 함께 쓰는 함수 하나나 데코레이터 하나에 둔다. 그러면 처리 함수를 읽는 쪽이 파일을 하나 더 열어야 하지만, 그래도 그렇게 둔다.

로그인 검사를 처리 함수마다 복사해 넣었다면, 나중의 변경은 그 복사본을 빠짐없이 찾아야 한다. 로그인 검사 하나를 빠뜨리는 것은 파일 하나를 더 여는 것보다 비싸다. 복사본이 더 안전한 선택인 때가 언제인지는 6장에서 본다.

옮길 수 없는 부분도 있다. 운영 담당자가 서버가 돌아가는 중에 값을 바꾼다거나, 문구를 번역가가 관리한다면, 그 부분은 그 사람들이 고칠 수 있는 파일에 남고 규칙은 나뉜 채로 있게 된다.

한 화면에는 크기 한도도 있다. 손님에 관한 모든 것이 들어 있는 `users.py`라면 세션은 그 파일을 한 구역씩 나눠 읽는 편이다. 파일 전체를 읽으면 컨텍스트 창이 다 차기 때문이다. <!-- 출처 없음: 세션이 긴 파일을 읽는 방식, 경향으로 적음 --> 그러니 한 번의 변경이 건드리는 줄만 한데 모은다.

이 장의 예처럼 작은 저장소에서는 세션이 그냥 모든 파일을 열 수도 있고, 그러면 세션은 규칙의 모든 부분을 본 것이다. 컨텍스트 창이 커지고 검색이 좋아지면 더 큰 저장소에서도 그럴 수 있게 될 것이다. 그때는 세션 앞에 문구 표가 놓여 있을 것이다. 그래도 함수 하나짜리 버전이라면 한 번 읽으면 되는 것을 세션은 세 번 읽어야 한다.
