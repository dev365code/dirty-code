# 13장. 동시에 달릴 때 깨지면 안 되는 것을 사람이 정한다

## 장면

붐비는 교차로를 1분에 차 마흔 대가 지나간다. 어느 운전자도 다른 차가 어디로 가는지, 다른 차의 엔진이 어떤 상태인지 모른다. 그래도 아무도 부딪치지 않는다. 모든 운전자가, 어느 운전자도 정하지 않은 두 가지를 따르기 때문이다. 신호와 차로다. 남북 방향과 동서 방향에 동시에 초록불이 켜지는 일은 없어야 한다는 것은 시청의 교통 담당자가 정했다.

어느 날 밤 신호등이 고장 나서 모든 방향에 노란불이 깜빡인다. 운전자들은 여전히 조심해서 운전한다. 저마다 속도를 줄이고, 살피고, 틈을 가늠하고, 지나간다. 그 판단 하나하나는 따로 떼어 보면 다 그럴 만하다. 그런 판단 둘이 교차로 한가운데에서 만난다.

내 서버는 같은 순간에 요청 둘을 처리하고, 내 저장소에서는 지금 AI 세션 셋이 일하고 있다. 동시에 일어나면 안 되는 일이 무엇인지는 누가 정했는가?

## 주장

> 여러 일이 동시에 돌아갈 때는, 그 사이에서 절대 일어나면 안 되는 일을 사람이 정하고 확인할 수 있는 것으로 적어 둔다. 요청 하나하나와 AI 세션 하나하나는 자기 자신만 보기 때문이다.

## 왜 그런가: 요청 하나하나와 AI 세션 하나하나는 따로 보면 맞고, 실패는 그 사이에서 일어난다

요청 하나를 처리하는 코드는 요청이 하나일 때나 천 개가 동시에 돌 때나 똑같이 읽힌다. 첫 요청이 아직 일하는 동안 같은 상품권에 대한 둘째 요청이 올 수 있다는 말은 함수의 글자 어디에도 없다.

그 함수를 쓰는 세션은 프롬프트와 파일을 보고 일한다. 세션은 자기가 쓴 방식대로 그 함수를 시험한다. 요청 하나를 보내고, 그다음 요청을 보낸다. 그 테스트들은 통과한다. 실패가 일어나려면 요청 둘이 특정한 순서로 얽혀야 하는데, 그 순서는 세션이 읽거나 실행한 어느 줄에도 없다.

쇼핑몰을 1년 운영한 사람은 그런 일이 일어난다는 것을 안다. 손님이 결제 버튼을 두 번 누른다. 휴대폰과 노트북이 같은 순간에 같은 상품권으로 결제한다. AI에게는 그 일이 나에게 일어났던 밤의 기억이 없다. 그러니 내가 아는 것은 보장으로 적어 두어야 한다. 이런 문장으로 적는다. "두 요청이 같은 순간에 와도, X는 절대 일어나지 않는다."

한 층 위에서도, 곧 AI 세션들 사이에서도 같은 일이 일어난다. 세션 하나는 싸기 때문에, 나는 저장소 하나에 세션을 여럿 돌릴 수 있다. 세션은 저마다 파일을 읽고, 정하고, 쓴다. 어느 세션도 다른 세션이 있다는 것을 모른다. 세션 둘이 폴더 하나를 같이 쓰면, 한 세션의 커밋이 다른 세션이 쓰다 만 파일을 쓸어 담을 수 있다. 세션마다 자기 가지에서 일하면, 둘 다 자기 테스트는 통과하는데 가지를 합치는 순간 서로를 망가뜨릴 수 있다.

두 경우 모두, 참여하는 쪽 하나하나는 따로 보면 맞다. 잘못되는 것은 그 사이이고, 어느 쪽도 그곳을 보지 않는다. 그 자리에서 절대 일어나면 안 되는 일이 무엇인지는 누군가 정해야 한다. 상품권이 들어 있는 돈보다 많이 나가도 되는지는 사업에 관한 물음이다. 그러니 쇼핑몰의 사람이 정한다.

## 코드: 요청 둘이 같은 잔액 확인을 통과하는 코드, 그리고 그 틈을 닫는 문장 하나

쇼핑몰은 상품권을 판다. 아래는 상품권에서 돈을 빼는 함수의 사람을 위한 버전과 그 테스트다. 금액은 원 단위 정수다. 이 목록은 이대로 실행된다. 테스트 둘은 통과하고 셋째는 실패한다.

```python
import sqlite3
import unittest


class InsufficientBalance(Exception):
    pass


# giftcards.py (사람을 위한 버전)
def redeem(db, card_id, amount):
    """상품권에서 amount원을 뺀다."""
    (balance,) = db.execute(
        "SELECT balance FROM gift_cards WHERE id = ?", (card_id,)
    ).fetchone()
    if balance < amount:
        raise InsufficientBalance(f"카드 {card_id}의 잔액은 {balance}원이고, 필요한 돈은 {amount}원이다")
    db.execute(
        "UPDATE gift_cards SET balance = ? WHERE id = ?", (balance - amount, card_id)
    )


# test_giftcards.py
def new_db():
    """50,000원이 든 상품권 한 장이 있는 데이터베이스."""
    db = sqlite3.connect(":memory:")
    db.execute("CREATE TABLE gift_cards (id TEXT PRIMARY KEY, balance INTEGER)")
    db.execute("INSERT INTO gift_cards VALUES ('card-1', 50000)")
    return db


def balance_of(db):
    return db.execute("SELECT balance FROM gift_cards WHERE id = 'card-1'").fetchone()[0]


class RedeemTest(unittest.TestCase):
    def test_redeem_lowers_the_balance(self):
        db = new_db()
        redeem(db, "card-1", 30000)
        self.assertEqual(balance_of(db), 20000)

    def test_redeem_refuses_more_than_the_balance(self):
        db = new_db()
        with self.assertRaises(InsufficientBalance):
            redeem(db, "card-1", 60000)
        self.assertEqual(balance_of(db), 50000)


class GapDB:
    """첫 UPDATE가 나가기 바로 전에 둘째 요청을 끼워 넣어 주는 연결."""

    def __init__(self, db, second):
        self.db, self.second = db, second

    def execute(self, sql, params=()):
        if sql.startswith("UPDATE") and self.second:
            second, self.second = self.second, None
            second()
        return self.db.execute(sql, params)


class GiftCardGuarantee(unittest.TestCase):
    def test_two_requests_at_once_never_pay_out_more_than_was_loaded(self):
        db = new_db()
        paid_out = []

        def request(conn):
            try:
                redeem(conn, "card-1", 30000)
                paid_out.append(30000)
            except InsufficientBalance:
                pass

        request(GapDB(db, lambda: request(db)))
        self.assertLessEqual(sum(paid_out), 50000)


if __name__ == "__main__":
    unittest.main()
```

`redeem`은 읽기 쉽다. 잔액을 읽고, 확인하고, 새 잔액을 쓴다. 사람이 말로 설명할 때와 같은 순서다. 앞의 두 테스트는 요청을 하나씩 보내고, 둘 다 통과한다.

셋째 테스트가 보장이다. 50,000원이 든 상품권에서 요청 둘이 저마다 30,000원을 빼려고 한다. `GapDB`는 둘째 요청을 정확히 한 자리에 끼워 넣는다. 첫 요청이 잔액을 확인한 뒤이고, 첫 요청이 쓰기 전이다. 이 테스트는 스레드를 쓰지 않는다. 그래서 둘째 요청은 돌릴 때마다 그 자리에 떨어진다.

일어나는 일은 이렇다. 첫 요청이 `50000`을 읽고 확인을 통과한다. 둘째 요청이 `50000`을 읽고, 확인을 통과하고, `20000`을 쓴다. 그다음 첫 요청도 `20000`을 쓴다. 두 요청이 모두 성공하고, 테스트는 `AssertionError: 60000 not less than or equal to 50000`으로 실패한다.

상품권의 잔액은 20,000원이라고 나오고, 그 숫자는 맞아 보인다. 쇼핑몰은 50,000원짜리 상품권으로 60,000원어치 물건을 내주었다.

AI를 위한 버전은 `redeem`만 바꾸고 다른 것은 바꾸지 않는다.

```python
# giftcards.py (AI를 위한 버전)
def redeem(db, card_id, amount):
    """상품권에서 amount원을 뺀다."""
    # 일부러 문장 하나로 썼다. SELECT 다음에 UPDATE를 따로 하면,
    # 함께 도착한 요청 둘이 모두 잔액 확인을 통과한다.
    done = db.execute(
        "UPDATE gift_cards SET balance = balance - ? WHERE id = ? AND balance >= ?",
        (amount, card_id, amount),
    )
    if done.rowcount == 0:
        raise InsufficientBalance(f"카드 {card_id}로는 {amount}원을 낼 수 없다")
```

이 함수로 바꾸면 테스트 셋이 모두 통과한다. 확인과 쓰기가 문장 하나라서, 그 사이에 둘째 요청이 끼어들 자리가 없다. 어느 요청이든 문장이 나중에 실행되는 쪽은 잔액 `20000`을 만나고, 아무 행도 바꾸지 못하고, 거절된다.

AI를 위한 버전은 내주는 것이 있다. 이 함수의 오류 메시지는 상품권에 얼마가 들어 있었는지를 말하지 못한다. 함수가 잔액을 읽은 적이 없기 때문이다. 9장은 그 값을 오류에 담으라고 한다. 잔액을 읽으려면 문장을 하나 더 실행해야 하고, 그 값은 메시지가 찍힐 때쯤에는 이미 낡았을 수 있다.

주석은 7장이 말한 이유로 달았다. 사람을 위한 버전이 더 자연스럽게 읽힌다. 그래서 이 파일을 읽기 쉽게 고쳐 달라는 요청을 받은 세션은 문장 하나를 다시 셋으로 되돌릴 수 있다. 주석은 왜 하나인지를 말하고, 세션이 그래도 되돌리면 셋째 테스트가 실패한다.

## 프롬프트: 함수를 요청하는 프롬프트, 보장을 넣은 프롬프트, 그리고 저장소 하나에서 여러 세션이 일할 때의 규칙

아래는 두 버전의 `redeem`이 모두 글자대로 채우는 프롬프트다.

```text
giftcards.py에 redeem(db, card_id, amount)를 추가해 줘. 상품권 잔액에서
그 금액을 빼고, 잔액이 모자라면 거절해.
```

사람을 위한 버전도 금액을 빼고, 잔액이 모자라면 거절한다. 프롬프트가 요청한 것은 그것뿐이다. 아래는 보장을 넣은 프롬프트다.

```text
giftcards.py에 redeem(db, card_id, amount)를 추가해 줘.

보장: 같은 상품권에 대한 요청 둘이 같은 순간에 도착해도, 상품권에서는
넣은 돈보다 많은 돈이 절대 나가지 않는다.

완료 기준: test_giftcards.py에 이런 테스트가 있다. 50000원이 든
상품권에서, 첫 요청이 잔액을 확인하고 쓰기 전 사이에 30000원짜리
둘째 요청이 실행되고, 둘 가운데 많아야 하나만 성공한다.
그 테스트가 통과하는 것을 보여 주기 전에, 읽고 확인하고 쓰는 순서로
짠 버전에서 그 테스트가 실패하는 것을 먼저 보여 줘.
```

보장은 쇼핑몰의 말로 쓴 한 문장이다. 완료 기준은 그 문장을 테스트로 바꾸고, 그 틈이 어디인지를 댄다. 마지막 문장은 테스트가 먼저 실패하는 것을 보여 달라고 한다. 이유는 14장에 있다. 한 번도 실패해 본 적 없는 테스트는 아무것도 시험하지 않고 있을 수 있다.

이 프롬프트는 보장을 어떻게 지킬지는 말하지 않는다. 문장 하나로 쓰든, 잠금을 걸든, 행에 버전 번호를 두든 그 테스트는 통과한다. 고르는 것은 세션이다. 무엇이 지켜져야 하는지와 그것을 어떻게 확인할지는 내가 정한다.

저장소 하나에서 여러 세션이 일할 때도 같은 종류의 문장이 필요하다. 아래 줄들은 규칙 파일에 넣는다. 규칙 파일은 저장소에 두고 AI가 일을 시작할 때 읽는 지시 파일이다.

```text
- 이 저장소에서는 다른 AI 세션들이 동시에 일하고 있다.
- 자기 작업 폴더(worktree)와 자기 가지에서만 일한다.
- 파일은 이름을 대서 스테이징한다. git add -A나 git commit -a를 쓰지 않는다.
- 자기 가지를 병합하지 않는다. 준비되면 나에게 알린다.
```

세 가지 결정은 나에게 남는다. 단순하고 서로 떨어진 일은 동시에 돌려도 된다. 돈, 환불, 저장된 데이터를 다루는 일은 한 번에 세션 하나에만 맡긴다. 그리고 병합은 한 사람이, 한 번에 가지 하나씩 하고, 병합할 때마다 테스트를 돌린다.

> **[실행 기록 자리: E14]** 프롬프트마다: 세션이 쓴 함수, 세션이 쓴 테스트, 세션의 보고에 요청 둘이 동시에 오는 경우가 언급되는지. 날짜, 도구, 모델.

## 근거: 두 요청 테스트는 사람을 위한 버전에서 실패하고, Git은 각자 통과하는 가지 둘을 import조차 안 되는 코드로 합친다

나는 위 목록을 `redeem`의 두 버전으로 각각 돌려 봤다. 사람을 위한 버전에서는 실행 결과가 `Ran 3 tests`와 `FAILED (failures=1)`이다. 두 요청이 모두 돈을 받고, 잔액은 `20000`으로 끝난다. AI를 위한 버전에서는 실행 결과가 `Ran 3 tests`와 `OK`다. 요청 하나가 돈을 받고 다른 하나는 거절된다.

세션들이 저장소를 같이 쓰는 경우도 작은 시험 셋으로 돌려 봤다. 세션 대신 보통의 Git 명령을 썼다. <!-- 2026-11-13 실행, Git 2.50.1, Python 3.9.6 -->

첫째 시험에서는 세션 둘이 폴더 하나를 같이 쓴다. 세션 A는 `refunds.py`에 함수를 쓰다가 만 상태다. 세션 B는 `shipping.py`의 변경을 끝내고 `git add -A`와 `git commit`을 실행한다. B의 커밋에는 파일 둘이 나온다. `refunds.py`와 `shipping.py`다. A가 쓰다 만 함수는 이제 B의 커밋 메시지 아래에 기록되어 있고, A가 `git status`를 쳐 보면 커밋할 것이 없다고 나온다.

둘째 시험에서는 세션마다 작업 폴더가 따로 있다. B의 커밋에는 파일 하나, `shipping.py`만 나오고, A에게는 자기가 쓰다 만 변경이 그대로 보인다.

셋째 시험에서는 세션마다 자기 가지에서 일한다. 세션 A는 `shipping_fee`의 이름을 `shipping_cost`로 바꾸고 테스트도 고친다. 세션 B는 `shipping_fee`를 부르는 `checkout.py`를 더한다. 가지마다 자기 테스트는 통과한다. Git은 충돌이 있다는 말 없이 두 가지를 병합한다. 두 가지가 서로 다른 파일을 건드렸기 때문이다. 합친 코드는 import에서 실패한다. `ImportError: cannot import name 'shipping_fee' from 'shipping'`이다. 테스트가 이것을 잡아낸 것은 둘째 병합 뒤에 테스트를 돌렸기 때문이다.

이 실행들은 그런 실패가 실제로 있다는 것과, 확인 하나하나가 무엇을 잡아내는지를 보여 준다. 프롬프트가 아무 말도 하지 않을 때 세션이 사람을 위한 버전을 얼마나 자주 쓰는지는 보여 주지 않는다. 그것은 실험 E14가 센다. E14는 상품권 일을 새 세션들에 세 가지 꼴로 준다. 위의 첫째 프롬프트, 첫째 프롬프트에 보장 문장을 더한 것, 그리고 둘째 프롬프트 전체다. 꼴마다 새 세션 10개에 준다. 세션이 보지 못하는 판정 테스트는, 첫 요청이 보내는 데이터베이스 문장들의 사이사이에 둘째 요청을 끼워 넣어 보고, 상품권에서 `50000`보다 많은 돈이 나가지 않는지 확인한다. E14는 두 요청을 모두 통과시킨 함수를 쓴 세션의 수와, 두 요청 테스트를 스스로 쓴 세션의 수를 센다.

> **[결과 자리: 실험 E14]** 날짜, 도구와 모델. 꼴마다 세션 10개 가운데: 두 요청 모두에 돈을 내준 함수의 수, 요청 둘을 쓰는 테스트를 쓴 세션의 수.

> **[저자 사례 자리]** 저장소 하나에서 AI 세션 여럿을 돌린 실제 사례: 저자가 더한 규칙과, 그 규칙을 낳은 사고.

## 사람이 할 일

- [ ] 돈이나 재고를 움직이는 기능마다 한 줄을 쓴다. "두 요청이 같은 순간에 와도, X는 절대 일어나지 않는다." 상품권에서는 들어 있는 돈보다 많은 돈이 나가지 않는다. 쿠폰은 두 번 쓰이지 않는다. 주문은 두 번 결제되지 않는다. 재고가 하나 남은 물건은 두 번 팔리지 않는다.
- [ ] 그 줄마다, 틈에 둘째 요청을 끼워 넣는 테스트로 바꾼다. AI에게 그 테스트를 쓰게 하고, 고친 코드를 받아들이기 전에 그 테스트가 옛 코드에서 실패하는 것을 본다.
- [ ] 보장을 사업의 말로 프롬프트에 넣고, 완료 기준에 요청 둘짜리 예를 넣는다. 어떻게 지킬지는 세션에게 맡긴다.
- [ ] 저장소에서 둘째 세션이 일을 시작하기 전에, 세션마다 작업 폴더를 따로 준다: `git worktree add ../shop-b -b session-b`. 위의 줄들을 규칙 파일에 더한다.
- [ ] 병합은 한 번에 가지 하나씩 하고, 병합할 때마다 테스트를 돌린다. 충돌 없이 병합됐다는 것은 가지들이 서로 다른 줄을 바꿨다는 것까지만 알려 준다. 코드가 여전히 돌아간다는 것은 알려 주지 않는다.

## 이 원칙이 깨지는 곳

보장에는 하나하나 값이 든다. 잠금을 걸면 둘째 요청이 기다린다. 결제 코드를 한 번에 세션 하나에만 맡기면 나머지 세션들은 줄을 선다. 그러니 무엇을 보장하지 않을지도 정한다. "이 상품을 산 손님이 함께 산 상품" 목록은 1분쯤 낡아도 된다. 문서의 오타는 세션 둘이 동시에 고쳐도 된다.

테스트는 내가 생각해 낸 틈만 확인한다. 이 테스트는 `UPDATE` 하나의 바로 앞에 둘째 요청 하나를 끼워 넣는다. 요청 셋이 겹치는 경우, 서버가 두 문장 사이에서 멈추는 경우, 운영의 데이터베이스가 다르게 설정된 경우에 대해서는 아무것도 말해 주지 않는다. 돈을 다룰 때는 데이터베이스 자체가 무엇을 보장하는지 묻고, 내가 실제로 쓰는 것과 같은 종류의 데이터베이스로 시험한다.

작업 폴더를 따로 주면 파일은 나뉘지만 다른 것은 나뉘지 않는다. 한 컴퓨터의 세션 둘은 여전히 테스트 데이터베이스, 포트 번호, 캐시 폴더를 같이 쓸 수 있다. 같이 쓰는 것마다 같은 물음이 필요하다. 여기서 동시에 일어나면 안 되는 일은 무엇인가?

모델이 좋아지면 이런 틈을 더 자주 알아챌 수 있고, 어떤 모델은 그것을 물어볼 것이다. 알아챘다고 쇼핑몰이 무엇을 원하는지가 정해지는 것은 아니다. 둘째 요청을 거절할 수도 있고, 기다리게 할 수도 있고, 상품권 잔액이 0 아래로 내려가게 두었다가 나중에 정산할 수도 있다. 어느 쪽인지는 쇼핑몰의 사람이 정한다.
