# 12장. 어디서 자를 것인가: 확인할 수 있는 크기로 맡긴다

## 장면

누나 결혼식에 가느라 서울에서 부산까지 400킬로미터를 운전한다. 나는 두 시간마다 휴게소에 들른다. 연료 게이지를 보고, 차를 한 바퀴 돌면서 타이어를 훑어본다. 들를 때마다 5분이 든다.

세 번째 휴게소에서 뒷바퀴 하나가 물렁해 보인다. 나는 옆의 주유소에서 바람을 넣고 다시 출발한다. 나는 쓸모 있는 사실도 하나 안다. 그 타이어는 두 시간 전에는 멀쩡했다. 그러니 무슨 일이 있었든, 그 일은 방금 달린 구간에서 일어났다.

친구는 같은 길을 한 번도 쉬지 않고 달린다. 부산을 100킬로미터 앞두고 차가 한쪽으로 쏠리기 시작한다. 친구는 그것이 언제 시작됐는지, 다른 데도 잘못된 곳이 있는지 알지 못한다.

AI에게 일주일 치 일을 프롬프트 하나로 맡길 때, 내 휴게소는 어디에 있는가?

## 주장

> AI에게 맡기는 일은 내가 확인할 수 있는 조각으로 자르고, 조각마다 명령 하나가 통과인지 실패인지 말해 줄 수 있는 자리에서 끝낸다.

## 왜 그런가: AI는 한 세션에 파일 스무 개를 바꿀 수 있지만, 사람이 확인할 수 있는 것은 명령이 통과와 실패로 가려 줄 수 있는 것뿐이다

AI는 한 세션에 파일 스무 개를 바꿀 수 있다. AI에게는 타이핑이 거의 공짜이기 때문이다(1장). 그러니 일의 크기는 이제 쓰는 쪽이 얼마나 쓸 수 있느냐로 정해지지 않는다. 내가 얼마나 확인할 수 있느냐로 정해진다.

나는 줄마다 읽어서 확인하지 않는다. 이 책은 내가 그 일을 그만두었다고 전제한다(1장). 나는 무언가를 돌려서 확인한다. 테스트를 돌리고, 답을 아는 예를 돌리고, 검색을 한다. 그런 확인은 소식을 하나만 준다. 통과이거나 실패다. 작은 변경 뒤라면 실패는 몇 줄을 가리킨다. 파일 스무 개를 바꾼 변경 뒤라면 같은 실패가 파일 스무 개를 가리킨다.

통과가 알려 주는 것은 더 적다. 통과는 누군가 생각해 낸 경우들이 맞게 나왔다고 말할 뿐이다. 큰 변경에서 그 "누군가"는 대개 코드를 쓴 세션이다. 테스트도 그 세션이 썼기 때문이다. 그 세션의 테스트는 그 세션이 알고 있던 곳을 확인한다. 세션이 열어 보지 않은 곳에는 새 테스트가 없으니, 거기서는 실패할 것도 없다(14장).

AI에게 기억이 없다는 점도 자를 이유를 하나 더한다. 긴 일은 중간에 멈출 수 있다. 세션이 사용 한도에 걸리거나, 노트북이 잠들거나, 세션이 엉뚱한 길로 가서 내가 멈춘다. 새 세션은 앞 세션이 어디까지 끝냈는지 기억하지 못한다. 일이 조각으로 잘려 있고 조각마다 커밋과 통과한 테스트로 끝났다면, 새 세션은 마지막 커밋과, 어느 조각이 끝났는지 적힌 목록에서 시작한다. 일이 한 덩어리였다면 새 세션은 반쯤 바뀐 저장소에서 시작하고, 저장소가 지금 어떤 상태인지를 읽어서 알아내야 한다.

그러니 프롬프트를 쓰기 전에 확인을 어디에 둘지부터 정한다. 자르기 좋은 자리는, 전에 통과하던 테스트가 모두 그대로 통과하고, 답을 아는 새 예 하나도 통과하는 자리다.

## 코드: 두 군데를 빠뜨리고도 OK를 찍는 한 덩어리 변경, 그리고 같은 변경을 네 조각으로 자른 것

이 장의 "코드"는 변경이다. 아래는 변경하기 전의 쇼핑몰이다. 이 목록은 `orders.py`, `shipping.py`, `refunds.py`, `settlement.py`와 테스트를 붙인 것이다. 이대로 실행되고 `Ran 4 tests`와 `OK`를 찍는다. 금액은 원 단위 정수다.

```python
import unittest
from dataclasses import dataclass


# orders.py
@dataclass(frozen=True)
class Order:
    prices: dict[str, int]  # 품목 이름 -> 정가(원)
    coupon_discount: int    # 주문 전체에 쓴 쿠폰 할인(원)

    @property
    def paid(self) -> int:
        """손님이 실제로 낸 돈(원)."""
        return sum(self.prices.values()) - self.coupon_discount


# shipping.py
def shipping_fee(order):
    """배송비(원). 손님이 낸 돈이 50,000원 이상이면 무료."""
    return 0 if order.paid >= 50000 else 5000


# refunds.py
def full_refund_amount(order):
    """주문 전체가 돌아왔을 때 환불할 금액(원)."""
    return sum(order.prices.values()) - order.coupon_discount


# settlement.py
def payout_total(orders):
    """이 주문들에 대해 결제사가 쇼핑몰에 줘야 하는 돈(원)."""
    return sum(sum(o.prices.values()) - o.coupon_discount for o in orders)


# test_shop.py
class ShopTest(unittest.TestCase):
    def setUp(self):
        self.order = Order({"keyboard": 30000, "mouse": 20000}, 5000)

    def test_paid(self):
        self.assertEqual(self.order.paid, 45000)

    def test_shipping(self):
        self.assertEqual(shipping_fee(self.order), 5000)

    def test_full_refund(self):
        self.assertEqual(full_refund_amount(self.order), 45000)

    def test_payout(self):
        self.assertEqual(payout_total([self.order]), 45000)


if __name__ == "__main__":
    unittest.main()
```

지금까지는 주문 하나에 같은 품목을 하나씩만 담을 수 있었다. 쇼핑몰은 주문 하나에 키보드 둘을 팔고 싶고, 나는 AI에게 한 줄을 써 보낸다.

```text
같은 품목을 여러 개 살 수 있게 해 줘.
```

이런 변경이 돌아왔다고 하자. 바뀐 것은 `orders.py`와 테스트 파일뿐이다.

```python
# orders.py
from dataclasses import dataclass, field


@dataclass(frozen=True)
class Order:
    prices: dict[str, int]  # 품목 이름 -> 한 개의 정가(원)
    coupon_discount: int    # 주문 전체에 쓴 쿠폰 할인(원)
    quantities: dict[str, int] = field(default_factory=dict)  # 품목 이름 -> 개수. 없으면 1개

    @property
    def paid(self) -> int:
        """손님이 실제로 낸 돈(원)."""
        total = sum(price * self.quantities.get(item, 1) for item, price in self.prices.items())
        return total - self.coupon_discount


# test_shop.py: ShopTest에 테스트 둘을 더했다
    def test_paid_counts_quantities(self):
        two = Order({"keyboard": 30000}, 0, {"keyboard": 2})
        self.assertEqual(two.paid, 60000)

    def test_two_keyboards_ship_free(self):
        two = Order({"keyboard": 30000}, 0, {"keyboard": 2})
        self.assertEqual(shipping_fee(two), 0)
```

세션은 `Order`에 `quantities` 칸을 더하고 `paid`가 그것을 세게 했다. `shipping_fee`는 `order.paid`를 읽으므로 바꿀 것이 없었고, 세션은 그것을 보여 주는 테스트를 썼다. 옛 테스트 넷은 손대지 않은 채로 통과하고, 새 테스트 둘도 통과한다. 실행 결과는 `Ran 6 tests`와 `OK`다.

함수 둘이 빠졌다. `full_refund_amount`와 `payout_total`은 `order.paid`를 부르지 않는다. 둘은 저마다 그 합계를 따로 계산하고, 어느 쪽 계산도 수량을 모른다. 키보드 둘짜리 주문에서 네 함수가 돌려주는 값은 이렇다.

| 함수 | 돌려주는 값 | 돌려줘야 하는 값 |
|---|---|---|
| `order.paid` | `60000` | `60000` |
| `shipping_fee(order)` | `0` | `0` |
| `full_refund_amount(order)` | `30000` | `60000` |
| `payout_total([order])` | `30000` | `60000` |

60,000원을 내고 주문 전체를 돌려보낸 손님은 30,000원을 받는다. 정산 보고서는 회계 담당자에게, 60,000원어치를 판 주문에 대해 결제사가 쇼핑몰에 줄 돈이 30,000원이라고 말한다.

내 앞에 놓인 것 가운데 그렇다고 말해 주는 것은 없다. 테스트는 `OK`를 찍는다. diff에는 파일 둘이 나오고, 두 변경 모두 그럴듯하다.

아래는 같은 변경을 네 조각으로 자른 것이다. 이 목록은 코드를 하나도 바꾸기 전에 쓴다.

```text
조각 1. orders.py: Order에 quantities를 더하고(없으면 1개), paid가 수량을 센다.
        확인: 옛 테스트 넷이 통과하고, 넷 가운데 고쳐진 것이 없다.
              새 테스트: 30000원짜리 키보드 둘, 쿠폰 없음 -> paid 60000.
조각 2. shipping.py: order.paid를 읽으므로 바꿀 것이 없을 수 있다.
        확인: 새 테스트: 30000원짜리 키보드 둘 -> 배송비 0.
조각 3. settlement.py: payout_total이 수량을 센다.
        확인: 새 테스트: 30000원짜리 키보드 둘인 주문 하나 -> payout_total 60000.
조각 4. refunds.py: full_refund_amount가 수량을 센다.
        확인: 새 테스트: 30000원짜리 키보드 둘, 주문 전체 반품 -> 환불 60000.
        키보드 둘 가운데 하나만 돌아오는 경우는 주인이 규칙을 정해야 한다. 기다린다.
```

조각 3과 4가 한 덩어리 변경이 빠뜨린 두 군데다. 이 둘이 목록에 있는 것은 내가 코드를 바꾸기 전에 물음 하나를 던졌기 때문이다. 어느 줄이 `prices`를 읽는가? 이 저장소에서는 명령 하나가 답한다.


```text

```

검색은 세 줄을 찍고, 줄 하나가 조각 하나가 된다.

조각 2는 다른 이유로 목록에 있다. 나는 쇼핑몰이 50,000원부터 무료 배송이라는 것을 안다. 그래서 바꿀 코드가 없더라도 키보드 둘이 무료로 배송되는 것을 보고 싶다.

조각 4의 마지막 줄은 어느 검색 결과에도 없다. 키보드 둘 가운데 하나가 돌아오는 경우를 다루는 코드는 없다. 오늘까지는 주문 하나에 둘을 담을 수 없었기 때문이다. 그 줄은 내가 직접 더한다. 손님은 물건을 돌려보낸다는 것을 내가 알기 때문이다.

이 목록은 열 줄이고, 사람은 그 열 줄을 모두 읽을 수 있다. 이만한 크기의 목록에는 "빠진 것이 무엇이지?" 하고 물을 수 있고, 회계 담당자에게 보여 줄 수도 있다. 파일 스무 개짜리 diff에는 어느 쪽도 할 수 없다.

## 프롬프트: 변경 전체를 맡기는 한 줄, 그리고 조각 3만 맡기는 프롬프트

한 줄짜리 프롬프트는 모든 것을 한꺼번에 맡긴다.

```text
같은 품목을 여러 개 살 수 있게 해 줘.
```

자르는 쪽에서는 프롬프트를 두 종류 보낸다. 첫째 종류는 아무것도 바꾸지 않는다. 목록을 달라고 한다.

```text
같은 품목을 여러 개 살 수 있게 하려고 해.
아직 아무것도 바꾸지 마. Order.prices를 읽거나 이 변경 때문에 바뀌어야
하는 함수를 모두 파일과 줄 번호와 함께 적어 줘. 함수마다 무엇이
바뀌어야 하는지 말하고, 내가 확인해 볼 수 있는 예를 하나씩 줘.
```

나는 그 목록을 바로잡고, 나만 아는 것을 더하고, 저장소에 `PLAN.md`로 저장한다. 그러고 나서 조각마다 프롬프트를 하나씩 보낸다. 아래는 조각 3의 프롬프트다.

```text

수량을 세게 고쳐 줘.

settlement.py와 test_shop.py만 바꿔.
이미 있는 테스트는 고치지 마. 그 가운데 하나가 실패하면 멈추고
이유를 말해 줘.

완료 기준: test_shop.py에 아래 경우가 들어 있고 python3 -m unittest가

  30000원짜리 키보드 둘인 주문 하나, 쿠폰 없음 -> payout_total 60000

그다음 PLAN.md에 조각 3이 끝났다고 표시하고, 커밋하고, 멈춰.
```

이 프롬프트에는 11장의 부분들이 들어 있다. 규칙, 파일, 하지 말 것, 완료 기준이다. 새로 들어간 것이 셋 있다.

이 프롬프트는 조각과 계획 파일의 이름을 댄다. 새 세션은 조각 1과 2에 대해 저장소가 말해 주는 것 말고는 아무것도 모른 채로 조각 3을 할 수 있다. 계획과 진행 상태를 파일에 두는 것은, 조각 2를 한 세션이 그 일을 했다는 것을 기억하지 못하기 때문이다.

이 프롬프트는 이미 있는 테스트를 고치지 못하게 한다. 옛 테스트는 이 조각이 맞는지를 견줘 보는 기준이다. 세션이 일을 끝내려면 옛 테스트를 고쳐야 한다면, 조각을 잘못된 자리에서 잘랐거나 요구 사항이 바뀐 것이다. 나는 그 일이 일어나기 전에 그 말을 듣고 싶다.

이 프롬프트는 어디서 멈출지를 말한다. 조각 3을 끝내고 계획에서 조각 4를 본 세션은 내친김에 그것도 할 수 있는데, 조각 4에는 주인을 기다리는 줄이 있다.

> **[실행 기록 자리: E13]** 한 줄짜리 프롬프트와 프롬프트 넷 각각에 대해: 세션마다 열고 바꾼 파일, 더한 테스트, 세션의 보고. 날짜, 도구, 모델.

## 근거: 두 군데를 빠뜨린 채로 테스트는 OK를 찍고, 조각 3과 4의 예는 실패한다

나는 변경의 두 가지 판을 위의 목록으로 직접 돌려 봤다.

한 덩어리 판에서는 실행 결과가 `Ran 6 tests`와 `OK`이고, 네 함수는 표의 값을 돌려준다. `60000`, `0`, `30000`, `30000`이다.

자른 판에서는 조각 3의 새 테스트가 `AssertionError: 30000 != 60000`으로 실패한다. `payout_total`이 `sum(o.paid for o in orders)`를 돌려주게 고치면 통과한다. 조각 4의 새 테스트도 같은 메시지로 실패하고, `full_refund_amount`가 `order.paid`를 돌려주게 고치면 통과한다. 조각 4가 끝나면 실행 결과는 `Ran 8 tests`와 `OK`다.

이 실행들은 확인 하나하나가 무엇을 알려 줄 수 있는지를 보여 준다. 한 줄짜리 프롬프트를 받은 세션이 그 두 군데를 얼마나 자주 빠뜨리는지는 보여 주지 않는다. 그 빠뜨림은 내가 손으로 예에 써넣은 것이다.

조각마다 커밋하면 무엇을 얻는지도 시험해 봤다. 나는 조각이 끝날 때마다 커밋했고, 조각 2에 실수를 하나 심었다. 배송 테스트를 더한 그 변경이 `shipping_fee`의 `>=`를 `>`로도 바꾼 것이다. 조각 4가 끝난 뒤에도 테스트 여덟은 모두 통과했다. 그런 다음 테스트에는 없는 확인을 하나 돌렸다. 딱 50,000원을 낸 손님은 무료로 배송된다는 확인이다. 그 확인은 실패했다. 그 확인을 `git bisect run`에 물렸더니 커밋 둘을 돌려 보고 조각 2의 커밋을 지목했다. <!-- 2026-11-13 실행, Git 2.50.1 --> 변경 전체가 커밋 하나였다면 같은 실패는 변경 전체를 가리켰을 것이다.

내가 손으로 써넣은 부분은 실험 E13이 잰다. E13은 수량 변경을 새 세션들에 세 가지 꼴로 준다. 첫째 꼴은 한 줄짜리 프롬프트다. 둘째 꼴은 계획 전체, 곧 네 조각과 조각마다의 예를 담은 프롬프트 하나다. 셋째 꼴은 조각마다 하나씩인 프롬프트 넷이고, 프롬프트마다 새 세션에 보낸다. 꼴마다 10번 돌린다.

실행 하나하나는 판정 테스트가 판정한다. 판정 테스트는 AI에게 보여 주지 않는 테스트이고, 나는 이것으로 결과가 맞는지 가린다. 이 판정 테스트는 키보드 둘짜리 주문과 옛 주문들로 네 함수를 확인한다. E13은 통과한 실행의 수를 센다. 실패한 실행마다, 그 실패가 바뀐 줄 몇 줄을 가리키는지도 기록한다. 앞의 두 꼴에서는 diff 전체이고, 셋째 꼴에서는 조각 하나의 diff다.

둘째 꼴은 계획이 하는 일과 자르기가 하는 일을 갈라 보려고 둔다. 둘째 꼴과 셋째 꼴이 똑같이 자주 통과한다면, 이만큼 작은 변경에서는 자르기가 AI의 성공에 보태는 것이 없는 것이다. 그러면 이 장의 주장은 자르기가 확인하는 사람에게 해 주는 일에만 기대게 된다.

## 사람이 할 일

- [ ] 파일을 둘 이상 건드리는 변경을 맡기기 전에, 목록만 달라고 하고 아무것도 바꾸지 않는 프롬프트를 먼저 보낸다. 그 목록을 사업을 아는 사람으로서 읽고, 어떤 검색으로도 나오지 않을 줄을 더한다.
- [ ] 조각마다 프롬프트를 쓰기 전에 확인부터 적는다. 내가 돌릴 명령과 그 명령이 찍어야 하는 것을 적는다. 확인을 적을 수 없다면 그 조각이 너무 크거나, 아직 정해지지 않은 규칙이 있는 것이다.
- [ ] 목록을 저장소에 저장한다. 조각마다 커밋과 목록의 표시로 끝낸다. 그러면 새 세션이 그 목록에서 시작할 수 있다.
- [ ] 조각마다의 프롬프트에서, 이미 있는 테스트를 고치지 못하게 하고 어디서 멈출지를 말한다.
- [ ] 나중에 확인 하나가 실패하면 Git에게 그 조각을 찾게 한다. `git bisect start <실패하는 커밋> <통과하던 커밋>`을 실행하고, 이어서 `git bisect run <확인 명령>`을 실행한다. Git은 그 사이의 커밋들에서 확인을 돌려 보고, 처음으로 실패하는 커밋을 찍는다. `git bisect reset`은 저장소를 원래대로 돌려놓는다.

## 이 원칙이 깨지는 곳

조각이 너무 작으면 내가 병목이 된다. 열 줄짜리 변경마다 내가 명령을 돌리고 출력을 읽을 때까지 기다려야 한다면, AI는 대부분의 시간을 기다리며 보낸다. 확인이 자동으로 돌아간다면 한 번에 더 많이 맡긴다. 세션은 조각 1부터 3까지의 테스트와 예를 나 없이 돌리고, 하나가 실패할 때만 멈출 수 있다. 그래도 목록은 내가 먼저 읽는다.

조각의 크기를 줄 수로 재면 틀린다. 함수 하나의 이름을 파일 200개에서 바꾸는 것은 큰 변경이지만, 명령 둘이면 확인된다. 검색은 옛 이름이 사라졌다는 것을 보여 주고, 테스트는 통과한다. 그런 변경은 한 조각으로 맡긴다. 환불의 반올림 방식을 바꾸는 열 줄짜리 변경은, 누군가 규칙을 정하기 전에는 확인할 방법이 아예 없다.

어떤 변경은 단계마다 옛 테스트가 통과하도록 자를 수 없다. 저장된 데이터의 모양을 바꾸는 변경이 그렇다. 한동안은 옛 데이터와 새 코드가 함께 돌아가야 하기 때문이다. 그런 변경에는 따로 계획이 필요하다. 데이터를 바꾸는 단계가 있어야 하고, 그 단계가 실패했을 때 되돌아갈 길이 있어야 한다. 이 장의 예는 `quantities`에 기본값을 줘서 그 문제를 피했다.

조각은 모두 통과하는데 전체는 실패할 수 있다. 계획에 있는 예는 저마다 함수 하나를 확인한다. 키보드 둘짜리 주문 하나를 결제에서 배송, 환불, 정산까지 따라가는 예는 그 가운데 없다. 그런 예 하나를 계획의 마지막 줄로 더한다.

모델이 좋아지면 더 큰 조각도 맞게 끝낼 것이고, 그러면 조각을 키울 수 있다. 조각 하나가 끝난 뒤에 사람이 확인할 수 있는 양은 모델이 좋아진다고 늘지 않는다. 그 양은 확인을 자동으로 돌릴 때 는다.
