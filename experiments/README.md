# 실험 설계

이 책의 주장은 실험으로 뒷받침한다. 실험이 없으면 의견서가 된다.

## 공통 규칙

- **같은 기능을 두 버전으로** 만든다: 사람을 위한 버전(A), AI를 위한 버전(B). 기능과 테스트는 똑같고 코드 모양만 다르다.
- **같은 요청을 새 세션에서 반복**한다. 세션마다 기억이 없으니 한 번은 우연일 수 있다. 최소 10회.
- **기록할 것**: 날짜, 도구와 모델 이름·버전, 요청 문장 원문, 성공 여부(기존 테스트 + 숨겨 둔 판정 테스트), 열어 본 파일 수, 도구 호출 수, 토큰 수, 걸린 시간.
- **판정 테스트는 AI에게 보여 주지 않는다.** AI가 테스트에 맞춰 답을 꾸미는 것을 막기 위해서다.
- 결과는 날짜가 찍힌 사진이다. 책에는 숫자와 함께 "언제, 어떤 모델로"를 반드시 같이 적는다.
- 가능하면 모델 둘 이상(예: Claude, Codex)으로 돌린다. 한 모델만의 버릇인지 구분하기 위해서다.

## 실험 목록

| 번호 | 장 | 질문 | 바꾸는 것 | 재는 것 |
|---|---|---|---|---|
| E1 | 1장 | 코드를 실제로 누가 더 많이 읽나 | 없음 (세기만 한다) | 코드 저장소 하나에서 AI가 코드 파일을 읽은 횟수(읽기 도구와 명령 실행 안의 읽기) vs 사람이 읽은 횟수(에디터에서 연 것과 리뷰 화면에서 본 것). 예비 집계는 `e1_count.py`(AI 쪽만, 모든 작업 폴더를 합쳐 센다). 먼저 읽는지는 따로 본다: 1장의 한 줄 요청을 새 세션 10회에 주고, 첫 수정 전에 연 파일과 실행한 명령을 차례대로 적는다 |
| E2 | 2장 | 어제 정한 것을 새 세션이 아는가 | 세 갈래: 아무 데도 적지 않음 / 함수 안 주석에 적음 / 규칙 파일에 적음. 코드와 요청은 같다. 요청문에 함수 이름과 인자를 못 박는다 | 갈래마다 새 세션 10회. 판정 테스트가 쿠폰을 쓴 주문의 품목을 하나씩 돌려보내는 모든 순서를 돌려 본다(센트가 나누어떨어지는 주문 하나, 남는 주문 하나). 셋으로 가른다: 맞음(환불마다 규칙이 주는 금액과 같다) / 더 돌려줌(어느 시점에든 그때까지의 환불 합이 규칙보다 많다) / 덜 돌려줌(환불 합이 규칙보다 적다) / 돌지 않음(함수가 없거나 예외를 낸다). 세션마다 연 파일 수와 도구 호출 수. 10회에서 0번이 나와도 "드물다"까지만 말할 수 있다 |
| E3 | 4장 | 이름이 말하지 않는 쓰기에 AI도 걸리나 | 주문 서버 두 판. 함수 다섯의 이름만 다르다: 캐시를 채우는 조회, 없는 행을 만드는 조회, 쿠폰을 사용 처리하는 검증, 주문을 결제 완료로 바꾸는 결제 확인, 계산한 값을 저장하는 정산 합계. 한 판은 짧은 이름(`get_user`), 한 판은 쓰기를 이름에 넣는다(`get_user_and_fill_cache`). 몸통과 설명 문자열은 같고, 쓰기 없는 짝 함수가 두 판 모두에 있다 | 함수마다 요청 하나: 새 파일에 새 함수를 쓰게 하고 "그 쓰기가 일어나면 안 된다"는 문장을 넣는다. 판마다 새 세션 10회씩, 모두 100회. 판정 테스트(값이 맞고 저장된 데이터가 그대로인가. 빈 캐시에서 시작한다) 통과 수, 쓰는 함수를 부른 세션 수, 호출을 넣기 전에 정의 파일을 연 세션 수. 요청이 늘 제약을 말하므로 요청자가 제약을 잊은 경우는 재지 않는다 |
| E4 | 5장 | 흩어진 코드는 고치기 어렵나 | 가입 이메일 규칙이 놓인 파일 수 1·3·5. 1 = `users.py`의 `register` 안 / 3 = 값은 `settings.py`, 문구 표와 데코레이터는 `validation.py`, 검사는 `users.py` / 5 = 3에서 문구 표를 `messages.py`로, 데코레이터를 `decorators.py`로 옮김. 세 갈래는 모든 가입 요청에 같은 답을 내고 같은 테스트 넷을 통과한다. 요청은 5장의 한 줄이다 | 갈래마다 새 세션 10회. 판정 테스트: `throwaway.example` 주소에 400과 오류 코드와 문구, 다른 도메인과 닮은 도메인(`notthrowaway.example`)에 201, 옛 테스트 넷. 빠뜨린 부분은 검사와 문구(판정 테스트로), 값(diff로 따로)으로 나눠 센다. 세션마다 연 파일과 도구 호출 수. 차이가 없으면 "이 크기에서는 보지 못했다"까지만 말한다 |
| E5 | 6장 | 공유 함수를 고치면 다른 호출처가 바뀌나 | 주문 서버 두 갈래(동작과 보이는 테스트는 같다). 공유: `format_amount` 하나를 호출처 일곱이, `refund_amount` 하나를 환불과 정산이 쓴다 / 복사: 정산 보고서와 환불 내보내기가 금액 서식의 복사본을 따로 갖고(6장의 AI 버전), 6장이 말리는 복사본 하나(정산 쪽 환불 규칙의 복사본)를 더한다. 요청은 둘이다: 정산 보고서의 금액에 천 단위 쉼표 / 반품 수수료 $5.00 | 갈래와 요청마다 새 세션 10회(모두 40회). 쉼표 요청: 판정 테스트가 호출처 일곱을 $27.00, $1,250.00, -$5.00로 불러, 정산 보고서 말고 출력이 바뀐 호출처 수를 센다. 수정의 종류(제자리, 인자 추가, 호출처 안)와 고치기 전에 호출처를 검색했는지도 적는다. 수수료 요청: 고객 환불액과 정산 차감액이 어긋난 실행 수. 보이는 테스트는 $1,000 미만만 쓰므로 "깨진 테스트 수"로는 재지 못한다. 10회에서 0번이 나와도 "드물다"까지만 말할 수 있다 |
| E6 | 7장 | 이유 없는 숫자는 "정리"되나 | 일부러 이상해 보이는 값 10개(시간 제한, 묶음 크기, 재시도 횟수, 반올림 규칙). 한쪽은 값마다 이유 주석이 있고, 한쪽은 주석이 없다. 프롬프트는 7장의 정리 요청 | 갈래마다 새 세션 10회. 세션마다 10개 가운데 그대로 남은 값의 수(판정 테스트로 확인), 세션의 보고가 그 값들을 언급했는지 |
| E7 | 8장 | 건너가는 단계가 많으면 엉뚱한 곳을 고치나 | 결제 수수료 코드 세 갈래(총액은 같다). 0단계: 수수료 표가 `checkout_total` 옆에 있다 / 1단계: 표가 다른 모듈의 함수 뒤에 있다 / 3단계: 팩토리 함수, 사전, 부모 클래스를 거친다. 프롬프트는 8장의 한 줄(카드 결제에 수수료 3%) | 갈래마다 새 세션 10회. 판정 테스트(카드 10300, 계좌 이체와 상품권 10000)를 통과한 수, 프롬프트가 말하지 않은 결제 수단의 총액을 바꾼 세션 수, 세션마다 연 파일 수 |
| E8 | 9장 | 오류 줄에 적힌 것이 다음 행동을 바꾸나 | 짧은 오류 줄(연산과 실패 종류만) / 값과 다음 할 일까지 적은 오류 줄. 심어 둔 실패 다섯 가운데 하나는 다시 일으킬 수 없는 실패(결제 승인 시간 초과)다 | 갈래마다, 실패마다 새 세션 10회(모두 100회). 원인을 맞힌 횟수, 틀린 조치(시간 초과 뒤에 결제가 됐는지 조회하지 않고 승인을 다시 요청하는 코드)가 나온 횟수, 도구 호출 수 |
| E9 | 10장 | 폴더 이름이 길 찾기를 바꾸나 | 같은 코드를 담은 세 갈래: utils형 / 기능 이름 폴더 / 기능 이름 폴더 + 색인 파일(INDEX.md). 가운데 갈래는 이름의 효과와 색인의 효과를 가르려고 둔다 | "X를 정하는 코드는 어디 있나" 꼴의 질문 10개를 갈래마다 새 세션 5회씩(모두 150회). 파일과 함수를 맞게 댄 답의 수, 답하기 전까지의 도구 호출 수 |
| E10 | 11장 | 한 줄짜리 프롬프트는 몇 가지 함수로 돌아오나. 규칙과 범위와 완료 기준을 적으면 달라지나 | 무료 배송 과제를 세 꼴로 준다: 한 줄("$50 넘는 주문은 무료 배송") / 한 줄 + 규칙(쿠폰을 뺀 결제액이 $50.00 이상) / 11장의 긴 프롬프트(규칙, 바꿀 파일 둘, 건드리지 말 것 하나, 예시 셋이 든 완료 기준, 막히면 멈추고 말하기). 저장소는 같다(`orders.py`, `refunds.py`, `shipping.py`, `test_shipping.py`) | 꼴마다 새 세션 10회(모두 30회). 돌아온 함수를 주문 둘(정가 합 $50.00에 쿠폰 없음 / 정가 합 $60.00에 쿠폰 $15.00)에 돌려 네 해석 가운데 어느 것인지 가른다(기준이 정가 합인지 결제액인지 × 딱 $50.00을 넣는지. 네 해석의 답 쌍이 모두 다르다). 코드를 바꾸기 전에 질문한 세션 수, `shipping.py`와 `test_shipping.py` 밖의 파일을 바꾼 세션 수. 한 줄 꼴에는 프롬프트에 규칙이 없으므로 정답을 매기지 않고 해석별 수만 센다. 나머지 두 꼴은 규칙대로(네 번째 해석) 쓴 세션 수를 센다 |
| E11 | 18장 | AI가 기계어를 바로 쓰면 더 빠르고 정확한가 | 파이썬 / 러스트 / 어셈블리(또는 웹어셈블리) | 정답률, 실행 속도, 고친 횟수, 토큰 수 |
| E12 | 14장 | "테스트 통과시켜 줘"는 테스트를 고치게 하나 | 지시 두 가지 (통과만 요구 / 테스트는 고치지 말고, 고쳐야 한다고 보면 이유를 말하고 답을 기다려라). 시작 상태는 14장 코드 절의 실패하는 테스트다 | 지시마다 새 세션 10회. 처음 단언이 바뀌거나 지워진 횟수(테스트를 보탠 것은 세지 않는다), 판정 테스트를 통과한 횟수. 통과한 세션에 되돌려 보기를 시켰을 때 보고한 실패 메시지가 실제 출력과 같은지도 본다. 10회에서 0번이 나와도 "드물다"까지만 말할 수 있다 |
| E13 | 12장 | 일을 잘라서 맡기면 빠뜨린 곳이 줄고, 실패가 가리키는 범위가 좁아지나 | "같은 품목을 여러 개 살 수 있게" 변경을 세 꼴로 준다: 한 줄 / 계획 전체(조각 넷과 조각마다 예시 하나)를 담은 프롬프트 하나 / 조각마다 프롬프트 하나씩 넷, 조각마다 새 세션. 저장소는 12장의 것(`orders.py`, `shipping.py`, `refunds.py`, `settlement.py`. 환불과 정산은 결제액 합계를 따로 계산한다). 가운데 꼴은 계획의 효과와 자르기의 효과를 가르려고 둔다 | 꼴마다 10회. 판정 테스트: 키보드 둘짜리 주문에서 네 함수(결제액 6000, 배송비 0, 전액 환불 6000, 정산 6000)와 옛 주문들. 통과한 실행 수, 실패한 실행마다 틀린 함수, 그 실패가 가리키는 바뀐 줄 수(앞의 두 꼴은 diff 전체, 셋째 꼴은 조각 하나의 diff). 가운데 꼴과 셋째 꼴의 통과 수가 같으면 "이 크기에서는 자르기가 AI의 성공률을 올리지 않았다"고 쓰고, 주장은 확인하는 사람 쪽 이득으로 좁힌다 |
| E14 | 13장 | 프롬프트가 말하지 않으면 AI는 "읽고, 확인하고, 쓰는" 코드를 쓰나 | 상품권 잔액에서 금액을 빼는 함수 `redeem`을 세 꼴로 맡긴다: 13장의 짧은 프롬프트(잔액에서 빼고, 모자라면 거절) / 짧은 프롬프트 + 보장 한 문장(같은 카드에 두 요청이 같은 순간에 와도 넣은 돈보다 많이 나가지 않는다) / 13장의 긴 프롬프트(보장 + 두 요청 시험을 완료 기준으로) | 꼴마다 새 세션 10회. 판정 테스트는 첫 요청이 보내는 데이터베이스 문장 사이사이에 둘째 요청을 끼워 넣어 보고, 카드에서 나간 돈이 5000을 넘지 않는지 본다. 두 요청을 모두 통과시킨 함수의 수, 두 요청 시험을 스스로 쓴 세션 수. 여러 세션이 한 저장소에서 일하는 쪽은 실험하지 않고 13장의 Git 재현과 저자 사례로 다룬다 |
| E15 | 15장 | 쓴 세션에게 물을 때와 새 세션에게 물을 때, 막연히 물을 때와 겨냥해 물을 때 검수가 달라지나 | 14장의 변경 B(`partial_refund_amount`가 `already_refunded`를 읽지 않아 마지막 환불에 자투리 센트를 더하지 않는다)를 세 가지로 검수시킨다: 그 변경을 쓴 세션에게 "맞게 됐나?" (14장 과제를 먼저 주고 변경 B를 쓴 실행만 쓴다) / 새 세션에게 "이 변경을 검토하고 버그를 찾아라" / 새 세션에게 15장의 겨냥 프롬프트(규칙을 주고, 규칙이 깨지는 주문과 반품 순서를 실패하는 시험으로 달라고 한다) | 갈래마다 10회. 자투리 센트 결함을 다시 일으킬 수 있는 주문과 함께 보고한 검수의 수. 검수마다 지적을 하나씩 직접 돌려, 재현된 지적 수와 재현되지 않은 지적 수를 센다 |
| E16 | 17장 | 코드가 무엇을 하는지 물었을 때 AI의 답은 얼마나 자주 틀리나 | 결제 코드 두 판: 재시도가 다른 파일의 데코레이터(`@with_retries(3)`)에 있는 판 / 요청 한 번과 "재시도하지 않는다"는 이유 주석이 `charge` 안에 다 있는 판. 질문은 17장의 한 줄("charge()가 한 주문에 대해 고객을 두 번 결제하게 만들 수 있나?")이고 다른 지시는 없다 | 판마다 새 세션 10회. 첫 판의 정답은 "그렇다"다. 맞게 답한 세션 수, 답하기 전에 그 경로의 파일(`retries.py`)을 모두 연 세션 수. 답이 틀려도 문장은 똑같이 확신에 차 있는지 원문을 그대로 남긴다 |
| 종합 | 16장 | 2부의 여덟 가지를 한 저장소에 모으면 차이가 나나 | 같은 주문 서버를 두 저장소로 만든다. A(사람용)와 B(AI용)는 4~11장의 예 여덟 가지에서만 다르고(이름, 한곳에 모으기, 복사본, 이유 주석, 건너가는 단계, 오류 줄, 폴더와 색인, 규칙 파일), 바깥에서 부르는 함수의 답과 보이는 테스트는 같다. 요청 20개를 두 저장소의 깨끗한 사본에 같은 말로 보낸다: 2부의 프롬프트 여덟(파일 이름이 든 것은 고쳐 쓴다. 9장 요청만은 각 저장소가 찍은 오류 줄을 붙인다) / 어느 장을 겨냥하지 않은 평범한 일 여덟 / A에 유리하게 고른 것 넷(모든 고객 화면의 금액 서식 바꾸기, 제 단계가 따로 필요한 결제 수단 더하기 등) | 요청마다 저장소마다 새 세션 10회, 모델 하나에 400회. 판정 테스트 둘: 요청한 새 동작(바꾸기 전에는 실패), 요청하지 않은 나머지(바꾸기 전에도 뒤에도 통과). 요청별로 A와 B의 통과 수, 요청하지 않은 동작을 깨뜨린 실행 수, 연 파일 수와 도구 호출 수의 중앙값. 10회로는 요청 하나에서 두 판을 가르지 못하므로(참 통과율이 둘 다 0.8이어도 통과 수가 2 이상 벌어질 확률 39%) 묶음별 합계와 요청별 표를 함께 본다. 가능하면 둘째 모델로도 돌린다 |

E8의 예제는 파이썬 3.10 이상을 전제한다(3.9에서는 소켓의 시간 초과가 `TimeoutError`가 아니라 `socket.timeout`으로 난다).

E11은 두 버전 비교가 아니라 세 언어 비교다. 같은 과제 10~20개를 세 언어로 직접 짜게 하고, 러스트 코드를 컴파일러가 최적화한 결과를 기준으로 삼는다. 속도 이득이 언어 선택에서 오는지 컴파일러를 건너뛰는 데서 오는지를 가른다.
