# 실험 설계

이 책의 주장은 실험으로 뒷받침한다. 실험이 없으면 의견서가 된다.

## 공통 규칙

- **같은 기능을 두 버전으로** 만든다: 사람을 위한 버전(A), AI를 위한 버전(B). 기능과 테스트는 똑같고 코드 모양만 다르다.
- **같은 요청을 새 세션에서 반복**한다. 세션마다 기억이 없으니 한 번은 우연일 수 있다. 최소 10회.
- **기록할 것**: 날짜, 도구와 모델 이름·버전, 요청 문장 원문, 성공 여부(기존 테스트 + 숨겨 둔 판정 테스트), 열어 본 파일 수, 도구 호출 수, 토큰 수, 걸린 시간.
- **판정 테스트는 AI에게 보여 주지 않는다.** AI가 테스트에 맞춰 답을 꾸미는 것을 막기 위해서다.
- 결과는 날짜가 찍힌 사진이다. 책에는 숫자와 함께 "언제, 어떤 모델로"를 반드시 같이 적는다.
- 가능하면 모델 둘 이상(예: Claude, Codex)으로 돌린다. 한 모델만의 버릇인지 구분하기 위해서다.

## 실험 목록

| 번호 | 장 | 질문 | 바꾸는 것 | 재는 것 |
|---|---|---|---|---|
| E1 | 1장 | 코드를 실제로 누가 더 많이 읽나 | 없음 (세기만 한다) | 코드 저장소 하나에서 AI가 코드 파일을 읽은 횟수(읽기 도구와 명령 실행 안의 읽기) vs 사람이 읽은 횟수(에디터에서 연 것과 리뷰 화면에서 본 것). 예비 집계는 `e1_count.py` |
| E2 | 2장 | 어제 정한 것을 새 세션이 아는가 | 세 갈래: 아무 데도 적지 않음 / 함수 안 주석에 적음 / 규칙 파일에 적음. 코드와 요청은 같다. 요청문에 함수 이름과 인자를 못 박는다 | 갈래마다 새 세션 10회. 판정 테스트가 쿠폰을 쓴 주문의 품목을 하나씩 모두 환불해 셋으로 가른다: 맞음(합이 낸 돈과 같고 환불마다 0 이상이며 정한 나누기 규칙대로) / 더 돌려줌 / 덜 돌려줌. 세션마다 연 파일 수와 도구 호출 수. 10회에서 0번이 나와도 "드물다"까지만 말할 수 있다 |
| E3 | 4장 | 이름이 거짓말하면 AI도 속나 | 이름이 동작과 맞음/어긋남 | 수정 성공률 |
| E4 | 5장 | 흩어진 코드는 고치기 어렵나 | 관련 파일 수 1·3·5 | 성공률, 놓친 곳 수 |
| E5 | 6장 | 공유 함수 수정이 다른 곳을 깨뜨리나 | 공유 함수 / 복사본 | 의도치 않게 깨진 테스트 수 |
| E6 | 7장 | 이유 없는 숫자는 "정리"되나 | 이유 주석 있음/없음 | 정리 요청 뒤 살아남은 비율 |
| E7 | 8장 | 간접 단계가 오독을 늘리나 | 간접 단계 0·1·3 | 성공률, 열어 본 파일 수 |
| E8 | 9장 | 로그 모양이 진단을 바꾸나 | 뭉뚱그린 오류 / 구조화된 로그 | 원인 진단 성공률, 단계 수 |
| E9 | 10장 | 폴더 이름이 길 찾기를 바꾸나 | utils형 / 기능 이름 + 색인 | 탐색 질문 정답률, 호출 수 |
| E10 | 11장 | 지시서가 구체적이면 재작업이 주나 | 한 줄 / 문단 / 범위·금지·완료 기준 | 재작업 횟수 |
| E11 | 18장 | AI가 기계어를 바로 쓰면 더 빠르고 정확한가 | 파이썬 / 러스트 / 어셈블리(또는 웹어셈블리) | 정답률, 실행 속도, 고친 횟수, 토큰 수 |
| E12 | 14장 | "테스트 통과시켜 줘"는 테스트를 고치게 하나 | 지시 두 가지 (통과만 요구 / 테스트는 고치지 말고 이유를 먼저 말하라) | 테스트 파일이 바뀐 횟수, 판정 테스트를 통과한 횟수 |
| 종합 | 16장 | E1~E10을 한 저장소로 모으면 | A 저장소 / B 저장소 | 수정 요청 20개의 성공률 |

E8의 예제는 파이썬 3.10 이상을 전제한다(3.9에서는 소켓의 시간 초과가 `TimeoutError`가 아니라 `socket.timeout`으로 난다).

E11은 두 버전 비교가 아니라 세 언어 비교다. 같은 과제 10~20개를 세 언어로 직접 짜게 하고, 러스트 코드를 컴파일러가 최적화한 결과를 기준으로 삼는다. 속도 이득이 언어 선택에서 오는지 컴파일러를 건너뛰는 데서 오는지를 가른다.
